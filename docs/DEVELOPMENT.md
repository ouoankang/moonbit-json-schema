# 开发历程：moonbit-json-schema 是怎么写出来的

> 本文是「可解释性」维度的开发历程回顾，说明这个项目是怎么一步步做出来、
> 哪些地方走了弯路、AI 在其中承担了什么角色。所有结论都对应仓库里可执行的
> 命令，数字以 `moon run --target js cmd/conformance` 的实测输出为准。

---

## 一、起点：为什么是 JSON Schema

选题的标准只有一条：**有没有一个外部权威标准能当尺子**。

JSON Schema draft 2020-12 的规范文本已经稳定，官方测试套件把「什么叫正确」
变成了 1301 条可机械验证的必测用例。这意味着项目的目标不是「写一个大概能用
的校验器」，而是「让这 1301 条全绿」——目标可量化、可验收、没有主观空间。
这对一个单人、一个月内要交付的项目来说，是最理想的项目形态：每一天的进度
都能用一个数字来度量。

MoonBit 生态当时没有一份经过官方套件验证的实现，这就是缺口本身。用 MoonBit
写应用、写工具链，要校验一份配置只能外挂 Node 或 Python 进程，白白丢掉了
编译到 wasm/native 的部署优势。

## 二、过程：从 98% 到 100%，靠的不是刷百分比

开发是按「先跑通骨架 → 逐文件转绿 → 抓静默错误」推进的。真正的转折点不在
写功能，而在发现**通过率高不代表对**。

最典型的一次：必测通过率已经到 98%，但我逐条核对 `JSTS_VERBOSE=1` 的
「期望 / 实际」输出时，发现 `refRemote.json` 里有 6 条用例被**静默跳过**。
根因是打断自引用环的 `active` 表用 `schema_path + 实例路径` 做键，而
`schema_path` 是相对根文档的——两份不同文档的根都是空串，于是「远程文档根」
的 `$ref` 被误判成自引用，整个远程 schema 被跳过。查不到引用时引擎按
「未实现」处理，而「未实现」不能算失败，于是那些期望「不通过」的用例全部
误判成通过。

这个 bug 让我定下一条规矩，贯穿了整个项目：

> **只看通过率是发现不了静默错误的。必须正反两面都测——期望「通过」的
> 要通过，期望「不通过」的也要真的不通过。**

之后每一处修复，都补了对应的回归用例：`remote_test.mbt` 覆盖跨文档 `$ref`
的别名与嵌套 `$id`，`schema_test.mbt` 覆盖注解与环判据，`regex_test.mbt`
覆盖 ECMA-262 语义分歧点。

## 三、四个最花时间的实现点

这几个是「写错了不报错、只会静默给错答案」的地方，各自对应套件里一组专门
用例（详见 README「几个值得说的实现点」）：

1. **注解必须带实例位置**。`unevaluatedProperties` 的语义建立在「这一层哪些
   属性已被认领」之上，而 `properties` 会向下求值子 schema。子结果的注解
   不能顺着树往上冒泡——`/foo` 位置认领的 `bar`，和根位置认领的 `bar` 是
   两回事。所以「合并子结果」被拆成 `merge`（同实例位置，收注解）和
   `require`（更深位置，只取通过与否、丢注解）两个方法。

2. **`$id` 只能解析一次**。`SchemaRef` 里的 `uri`（节点所在资源地址）和
   `base`（求值该节点时的解析基准）是两回事，混用会让远程文档的 `$ref`
   解析出多一层目录、静默失败。

3. **打断自引用环的判据要能唯一定位一个节点**（就是上面那个 98% 的坑）。

4. **动态作用域不只在 `$ref` 处压栈**。`$dynamicRef` 的目标是最外层同名
   `$dynamicAnchor`，而 `if`/`then`/`$defs` 里用 `$id` 开出的资源是「走进去」
   的、不经过任何 `$ref`，所以压栈必须在节点自带 `$id` 时发生。

另外两个横切决策也值得一提：**正则引擎自己写**（`pattern` 要按 ECMA-262
语义解释，`wasm` 目标上没有宿主正则可用，且宿主正则的 `\d`/`\w` 语义在跨
语言时不一致）；**`$vocabulary` 在入口处裁剪关键字**（与其给 1500 行里每个
关键字套条件，不如在 `eval_object` 入口把未启用词汇表的关键字去掉）。

## 四、format 断言：把「默认是注解」这件事做对

`format` 是 draft 2020-12 里最容易做错的关键字。它的默认语义是**注解**，
不是断言——只有元 schema 显式声明 `format-assertion` 词汇表时才升级为断言。
更微妙的是，`$vocabulary` 里 `format-assertion` 写 `true` 还是 `false` 对
「本实现认识这个词汇表」这件事**没有影响**，官方 `format-assertion.json`
明确要求两个元 schema 产生完全相同的校验结果。

实现时用 `dialect_of` 识别 `format-assertion` 词汇表（声明即生效，不认布尔值），
并给一致性测试台加了一个 `force_format` 开关——因为 `optional/format/*` 的
用例 `$schema` 都指向标准元 schema（声明的是 format-annotation），只有强制
启用才能跑分。这个开关只服务于测试台，普通用户路径语义不变。

`format.mbt` 里 15 个格式全部手写、按码点语义、不依赖宿主正则，最终把
可选用例从 567 条推到 929 条（90.8%）。

## 五、AI 在其中承担了什么

代码和文档是在 AI 助手（WorkBuddy）辅助下完成的，但分工是明确的：

- **AI 做「高吞吐的实现与查证」**：把规范条款翻成实现、跑测试、缩小缺陷范围、
  起草文档。生成物都带生成脚本——`unicode_categories.mbt` 由
  `gen-unicode-categories.mjs` 生成，`meta_docs.mbt` 由 `gen-metaschema.mjs`
  生成，两份脚本都带自检、重跑可复现。
- **人做「定性判断」**：目标、范围取舍（比如 format 要不要做、IDN 做不做）、
  每个 bug 的根因定性（「注解不该冒泡」是设计问题，不是补丁问题）。

一个具体的例子能说明这种分工：浏览器交付物这条链路上，曾有一个只在 JS
后端才暴露的 bug——MoonBit 的 `String[i]` 返回的是 UTF-16 码元而不是 `Char`，
`"https"` 会被 `s[i].to_string()` 输出成 `"104116116112115"`。`moon test`
跑在 wasm 目标上，**完全覆盖不到这一层**，是页面的 smoke 检查把它抓出来的。
AI 能快速定位到「转义函数把码元当字符」，但「为什么单元测试没兜住」这个判断
——即测试矩阵必须覆盖多后端——是人做的，也正是这类判断决定了项目的工程质量。

## 六、如果重来一次，会怎么做

1. **测试台先于实现写好。** 一致性测试台（`cmd/conformance`）其实是个极好的
   开发工具：`JSTS_ONLY=<子串>` 只跑单个文件、`JSTS_VERBOSE=1` 逐条打印
   期望/实际。早一点把它做成「调试器」而不是「最后跑分的工具」，能省掉大量
   猜。
2. **更早意识到「静默通过」的杀伤力。** 98% 那个阶段如果只看百分比就收工了，
   交付的就是一个有隐患的实现。正反两面都测这件事，应该从第一天就立为规矩。
3. **IDN/IRI 应该一开始就明确定为「范围外」。** format 这块的 IDN 需要完整
   的 punycode 和 IDNA 表，是个独立的工程量级，早一点在 Scope 里划清边界，
   就不用在最后阶段纠结「做还是不做」。
